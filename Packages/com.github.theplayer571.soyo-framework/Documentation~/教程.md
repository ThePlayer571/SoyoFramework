## 为什么需要框架？

项目混乱的根源在于 *耦合*，耦合的本质是 *依赖*。

框架 **限制**了层级间的依赖关系，从而降低耦合、保持项目整洁。

总结：框架设计出多个层级，你遵循这些层级的规则写代码，从而让项目尽可能保持整洁。

## SoyoFramework 层级介绍

一共有以下层级：

- 后端：
    - Aggregate：存储全局数据；运算绝大部分游戏逻辑。
- 前端：
    - ViewController：将数据转换为表现；接受玩家输入。
- 通信方式：
    - Command：封装玩家输入，向 Aggregate 传递信息。
    - Event：事件机制，允许跨层级通信。

我们会依次介绍。

### Aggregate - 聚合

#### 聚合的概念

**Aggregate** 不是 SoyoFramework 的特定术语，而是软件工程的一个重要概念。

- 抽象地说：Aggregate 是一组相关领域对象的集合。
- 形象地说：现在有一大堆业务，它们的存在都是为了做同一件事，那我们就能称它们的整体为 *一个聚合 (Aggregate)*。
- 举个例子：贪吃蛇小游戏中，有贪吃蛇、地图、食物、计分板等业务，它们的存在都是为了实现贪吃蛇游戏，因此它们可以被称为
  *贪吃蛇游戏聚合*。

#### 为什么需要聚合？

在贪吃蛇游戏中，蛇、地图等业务相互依赖耦合，如果我们不将它们组织为一个聚合，那么它们之间的依赖关系就会变得非常复杂。

规定：

- 聚合内部随意耦合。
- 聚合可以依赖于其他聚合，但不关注其他聚合的内部实现。

> SoyoFramework 的聚合与软件工程的聚合，在定义上有细微区别。

#### 聚合的组成

在 SoyoFramework 中，聚合由 **AggregateMember 聚合成员** 组成。

一个聚合通常存在多个成员，其中必然包含一个特殊的成员，叫做 **AggregateRoot 聚合根**。

聚合根是聚合的根部，直接或间接管理了所有成员。

我们以贪吃蛇游戏为例，可以这么设计聚合：

```text
- SnakeGame 贪吃蛇游戏 - Root
    - Map 地图 - Member
        - Snake 贪吃蛇 - Member
        - Food 食物 - Member
    - ScoreBoard 计分板 - Member
```

#### 在 SoyoFramework 中构建聚合

有两个关键接口：

- `IAggregateMember`：聚合成员接口。
- `IAggregateRoot`：聚合根接口，继承自 `IAggregateMember`。

聚合类必须继承这两个接口之一。

SoyoFramework 对这两个接口编写了默认实现，分别是：

- `AggregateRoot`：聚合根基类。
- `AggregateMember<TRoot>`：聚合成员基类。TRoot即对应的聚合根的类型，为方便Member引用Root而设置。

我们以贪吃蛇游戏为例：

```csharp
public class SnakeGame : AggregateRoot
{
    public Map Map { get; private set; }
    public ScoreBoard ScoreBoard { get; private set; }
    public void StartGame() { ... } // 开始游戏
    public void EndGame() { ... } // 结束游戏

    public SnakeGame()
    {
        Map = new Map(this);
        ScoreBoard = new ScoreBoard(this);
    }
}

public class ScoreBoard : AggregateMember<SnakeGame>
{
    public int Score { get; private set; }
    public void AddScore(int value) { ... } // 增加分数

    public ScoreBoard(SnakeGame root) : base(root) { }
}

public class Map : AggregateMember<SnakeGame>
{
    public List<Vector2Int> Walls { get; private set; } // 墙壁坐标
    public Snake Snake { get; private set; }
    public Food Food { get; private set; }

    public Map(SnakeGame root) : base(root)
    {
        Snake = new Snake(root);
        Food = new Food(root);
    }
}

public class Snake : AggregateMember<SnakeGame>
{
    public List<Vector2Int> Body { get; private set; } // 蛇身坐标
    public void Move(Vector2Int direction) { ... } // 移动

    public Snake(SnakeGame root) : base(root) { }
}

public class Food : AggregateMember<SnakeGame>
{
    public Vector2Int Position { get; set; } // 食物坐标

    public Food(SnakeGame root) : base(root) { }
}
```

#### 设计聚合的技巧

聚合的边界往往难以确定：一个聚合通常可以拆成多个聚合，多个聚合通常可以组合成一个聚合。

如何设计聚合？这是一个工程上的难题，并没有通解，但有一些经验法则，我列举一些公认正确的经验：

1. 聚合的边界应该按照业务语义来划分。
2. 聚合应该尽可能小，小到“再小就写不了代码了”。
3. 不要为了追求完美而频繁修改聚合的边界。

### ViewController - 表现控制器

#### 表现层的概念

表现层指玩家直接接触的部分，通常是 画面、音效、UI、动画等。

我们把表现层称为 *前端*，把 Aggregate 所在的层级称为 *后端*；之后我们会频繁使用这两个术语。

后端处理逻辑，前端处理表现与交互，这是一个非常好的分层。

#### ViewController 的概念

主流框架规划表现层的方案有很多，可以说并没有一个标准答案。 比较经典的有 MVC、MVP、MVVM 等，这里不展开讨论。

SoyoFramework 使用了 `ViewController` 的机制来处理表现层，这是作者原创的方案。

ViewController 是一个层级，而不是一个具体的类。

#### ViewController 的设计理念

与主流软件框架不同，SoyoFramework 的 ViewController 设计更适合游戏开发 这种表现层极为复杂的场景。

**ViewController 应当处理大部分的表现逻辑，尽可能让后端的代码保持简洁。**

- 举一个例子就懂：

Minecraft 的物品栏，当我们拿起一个物品时，我们可以随意拖动这个物品。拖动意味着物品的 *位置*发生了改变，这个 *位置*
的信息应该传入后端吗？

答案是不应该。因为后端根本不关心这个物品在屏幕的哪里，后端只在乎它在物品栏还是手上，因此 *拖动位置*的逻辑应该完全交给
ViewController 处理。

在一些更极端的情况下，比如有一个点一下就+1的按钮，它的值显然是游戏逻辑的一部分，但如果后端不需要读取它的值，它依旧可以交给
ViewController 处理。

#### 在 SoyoFramework 中构建 ViewController

有一个关键接口：

- `IViewController`：表现控制器接口。

实现这个接口的类被认为是 ViewController。

当然，我们通常不会直接实现接口，而是继承以下基类：

- `MonoVController`：意思是 MonoBehaviour + ViewController

框架推荐所有 ViewController 都是 MonoBehaviour。
